# AGENTS.md — правила для ИИ-агентов (сайт Блажевича)

## Что это за проект

Статический сайт о Владиславе Блажевиче (1881–1942), тромбонисте и педагоге. Русская и английская версии, каталог нот (панель поиска и фильтров убрана по просьбе владельца 13.11.2026, не возвращать). Собирается `build.py` из `src/` (Python 3, только стандартная библиотека).

- **Прод:** https://blazhevich.tech — обновляется ТОЛЬКО владельцем вручную (workflow «ПРОДАКШЕН: публикация deploy/prod» в GitHub Actions).
- **Тест:** https://test.blazhevich.tech — после каждого push в `main` репозитория `camadxu/blazhevich-site` CI сам пересобирает ветку `deploy/test`, и хостинг забирает её сам по вебхуку (автодеплой работает, по отчёту владельца от 12.11.2026); кнопка Deploy в hPanel остаётся запасным способом. Тестовая версия — черновая сборка: `noindex,nofollow` + плашка «не опубликовано». Это норма, а не дефект: тест-сайт не должен индексироваться поисковиками.

## Безопасность — абсолютные запреты (установлены владельцем)

- Никогда не запрашивай, не принимай и не используй: пароль Hostinger, FTP-пароль, SSH-пароль, доступ к файловому менеджеру hPanel с правом записи, полный доступ к аккаунту хостинга.
- Всё, что требует доступов к хостингу (создать Git-конфиг в hPanel, добавить deploy-ключ, настроить вебхук, залить файлы вручную), делает владелец лично. Твоя роль — подготовить изменения и дать владельцу готовые шаги.
- Не добавляй в репозиторий и не запрашивай никакие секреты. Схема деплоя не требует секретов: хостинг сам забирает код по read-only deploy-ключу, который владелец добавляет в GitHub вручную.
- Не пушь в ветки `deploy/*` вручную — их пишет только CI.

## Обычный цикл работы

1. Вноси изменения в `src/` и `assets/`. **Не редактируй `site/` руками** — он полностью генерируется `build.py`.
2. Локально проверь:
   ```
   python build.py
   python tools/check_site.py
   python tools/test_v3.py
   ```
   Все три команды обязаны пройти без ошибок. `test_v3.py` нужно запускать сразу после сборки с теми же аргументами `--release/--domain/--lastmod` (или задать их через `BLZ_DOMAIN`/`BLZ_LASTMOD`) — он проверяет воспроизводимость пересборкой.
3. Коммит в рабочую ветку и push в `camadxu/blazhevich-site` (тот же репозиторий, где `main` и CI; форк `camadxy/blazhevich-site` больше не используется — у агента там только чтение). Затем PR в `main`; вливает владелец. CI собирает `deploy/test`, хостинг выкладывает её на тест-сайт автоматически.
4. Владелец смотрит тест-сайт. Публикация в прод — только владелец запускает workflow «ПРОДАКШЕН: публикация deploy/prod».
5. В `main` агенты напрямую не пушат: только рабочая ветка, вливает владелец. Хостинг, CI, вебхуки и deploy-ключи живут в `camadxu/blazhevich-site`; подключение hPanel не трогать.
6. `TEST-RESULTS.json` генерируется `test_v3.py`, в репозиторий не входит.
7. Прямой SSH до github.com с рабочих машин не ходит — git по https. Ошибка «remote rejected … commit_refs_rules» бывает транзиентной — повторить пуш.

- История: на диске `D:` дважды (22–23.11.2026) зафиксирована порча файлов «на месте» с сохранением размера и mtime, том помечался dirty; записанные там git-файлы побиты. `D:\blazhevich-site` и прочие D:-пути проекта для работы не использовать (в `docs/PLAN.md` путь `D:\blazhevich-site` упомянут исторически).

## Команды сборки

- Черновик (для теста): `python build.py`
- Публичная (для прода): `python build.py --release --domain https://blazhevich.tech --lastmod ГГГГ-ММ-ДД`
- `--lastmod` — дата содержательной редакции, а не случайное число.
- Сборка детерминированна: повторный запуск с теми же аргументами даёт байт-в-байт тот же результат (в том числе на Windows — сборщик принудительно пишет LF).
- На русской Windows-сборке нужен UTF-8: `py -X utf8 build.py …`, иначе cp1251 падает на кириллице.

## Контент-дисциплина

- Факты — только из источников; сохранять происхождение фактов; разночтения источников не сглаживать без проверки; даты изданий не унифицировать без основания.
- Статусы сложности нот не выдумывать: сейчас все записи «не оценено по нотам».
- Написание бренда: владелец менял его с «Blszhecich» на «Blazhevich» — использовать Blazhevich.
- Исторические документы (README/HANDOFF версий v2–v6, START_HERE, V3/V5/V6, SCHOOL-DOSSIERS, TASK-HOSTINGER-DNS) удалены из дерева 24.11.2026 и доступны в истории git; в них фигурирует домен blazhevich.space — прошлое имя проекта, актуальный: blazhevich.tech. Действующие документы — в `docs/`; исследования агентов — в `docs/research/`.

Биография — отдельная страница `biography.html` / `en/biography.html` (полная, с полосой фактов; правится в `src/ru/biography.html` и в секции биографии `src/en/page.html`); стаба `biography.html` и 301 в htaccess больше нет. - **«Лента»** (17.11.2026, `docs/PLAN.md`, этап «Лента»): выпуски лежат в `data/news/ГГГГ-ММ-ДД.json`, их пишет `tools/news_agent.py` (только стандартная библиотека, без ключей; источники — `data/news/sources.json`, основание — `docs/research/brass-news-sources.md`). Пока выпусков нет, сборка ничего не добавляет. Когда есть — `build.py` ставит панель «Лента» на главной после вступления, собирает `/news/`, `/news/ГГГГ-ММ-ДД.html`, `/feed.xml`, `news/today.json` и добавляет выпуски в sitemap. Панель без JavaScript показывает запечённый выпуск; скрипт только фильтрует по инструментам и подтягивает более свежий `news/today.json`. Атрибуты — только `data-agent-*`. Выдуманные новости на сайт не ставить: пробный выпуск для проверки вёрстки лежит в `tools/fixtures/news/` и подключается только явно: `python build.py --news-dir tools/fixtures/news`. Поле `summary` сборщик новостей не заполняет (пересказ без языковой модели невозможен) — карточка тогда состоит из заголовка, источника, даты и ссылки.

- **Реестр трудов** (решение владельца 21.11.2026): «локальная база» — это реестр `data/works.json` (схема + происхождение файлов), не картотека цитат и не офлайн-копия библиотеки.

- `src/` — исходники страниц и стилей; `assets/` — изображения, шрифты, og-image; `data/` — реестр трудов и лента; `files/` — файлы прямых ссылок (ноты, записи), копируются в сборку как есть; `tools/` — проверки и генераторы; `build.py`, `enhancements.py` — сборщик; `docs/` — документация и исследования.
- `.github/workflows/deploy-test.yml` — автодеплой теста при push в `main`; `.github/workflows/deploy-prod.yml` — ручная публикация прода; `.github/scripts/publish-artifact.sh` — публикация артефакт-веток `deploy/*`. Файлы `.github/workflows/*` напрямую не менять (у токена нет scope `workflow` — пуш таких правок GitHub отклонит).
- `.deploy/htaccess` — шаблон `.htaccess` для деплой-веток (ErrorDocument 404, режим 503 «сайт временно закрыт», блокировка служебных каталогов Git, 301 с `www.` на основной домен, 301 со старых адресов `scores/concertos/usa` на новые страницы; HTML-стабы в сборке остаются — они работают при локальном предпросмотре без Apache). Регресс-тест режима 503: `tools/test_maintenance.py`.
- `deploy/test` и `deploy/prod` — артефакт-ветки, их корень = собранный сайт + `.htaccess`; именно их подключает Hostinger.
- Порядок подключения GitHub + Hostinger: `docs/DEPLOY.md`. План работ: `docs/PLAN.md` (шапка — актуализация на 24.11.2026).
